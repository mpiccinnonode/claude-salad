# buddy plugin — dev notes

A mod: function hooks only. Needs Claude Code ≥ 2.1.299 (a `Button` holding coloured `Text` children, and `Text mono`; 2.1.296 and older refuse it).

- `hooks/register.tsx` reads the options into one `Ctx` and wires events, nothing else. `commands.ts` answers `/buddy <verb>` (one function per verb), `view.tsx` draws the band, `state.ts` holds the session's atoms, `crew.ts` the store and the buddies file (hatching, crew, evolution), `dream.ts` the Haiku prompts, `words.ts` every user-facing line in both languages. What they draw comes from pure modules that the tests drive directly.
- `hooks/bones.ts` is the original roll (wyhash → mulberry32, salt `friend-2026-401`) over the original 18 species. coding-buddy's list has 20, which changes every roll, so keep 18. `bones.test.ts` pins reference values computed with coding-buddy's engine. New species go in `ALL_SPECIES` only: eggs (`rollNew`), the buddies file and `/buddy add` accept them, `roll` never picks them.
- `hooks/rigs.ts` rigs every species in `ALL_SPECIES`, plus evolution stages keyed `species:rarity` (`rigOf` picks the highest at or below the buddy's rarity): each part has its variants, a rhythm, an optional colour, and per-mood pins (`pet`, `poke`, `asleep`, `working`). `hooks/sprite.ts` is the one engine on top: eyes, hop, hat, hearts, sleep. `rigs.test.ts` checks every variant combination keeps a row 12 cells wide and that every mood moves part of the body.
- `hooks/friends.ts` parses and patches the buddies file (`buddiesFile`), and turns a structured personality into prompt text. `upsert` keeps fields it does not know: the file is the user's.
- The buddies file is the one source of every buddy's name, species and personality; the store keeps only what is rolled or counted (`born`, `together`, `crew`), keyed by `keyOf(name)`. In `crew.ts`, a file buddy without a `born` entry is an egg; `hatchNew` spends one, rolls a random seed and, when the entry has no personality, asks Haiku (`dreamUp`) and writes it back. `withOriginal` runs once (`moved` flag): it moves 0.8's original from `born['']` (plus 0.8's `name`/`personality`/`species` overrides, read as `o.old`; they stay declared in `userConfig` because undeclared options never reach `register`) to the top of the file and rekeys `born`, `together` and `crew`; a new user's first buddy hatches free the same way. A born buddy still without a personality (Haiku failed at hatch) is dreamt again at every session start by `soulUp`. The store has no compare-and-set, so sessions started together all run it: a twin already at the top of the file is reused, and a session that finds `born` already rekeyed only sets `moved` (`settled`). Before that it reads `~/.claude.json` once (`migrated` flag) so users of 0.2.0 keep their buddy; never read it anywhere else. The key `''` is now only the stand-in blob (`crewOr` in state.ts) shown while nobody is hatched; it never counts turns.
- Turns, not sessions, are what counts (`eggs`, `evolvesIn`, `perEgg`/`perEvolve` are turns). The store has no compare-and-set, so no counter is read-modify-written: each session writes only its own `tally:<id>` (`{ all, by: { buddyKey: n } }`, `countTurnTogether` on every main-loop `turn.complete`) and a total is the sum of every tally (`turnsTogether`, `togetherOf`). 0.9's `sessions`, `together`, `eggBase` and `born[].at` are read, never written again, each session worth `TURNS_PER_SESSION` turns; `eggAt` and `born[].ats` are their turn-based successors, and `zero` holds what a removed buddy had so one added again under its name starts over. Tallies are never folded together (`ponytail:` in crew.ts). Verified with real processes (Claude Code 2.1.310, isolated `CLAUDE_CONFIG_DIR` and `HOME`): 6 and then 12 `claude -p` started at once left every `tally:<id>` in the store and one original in the buddies file, and `$.store.get` rereads the file, so a tally written by another process shows in the band within `REFRESH_BEATS`. That was a burst of one-turn runs, not a proof; if tallies are ever seen missing, the fallback is one file per session through `$.fs`.
- The band follows the disk: `beat` calls `refresh` every `REFRESH_BEATS` (state.ts), which resolves the crew and what is ready again and updates the `members` and `ready` atoms only when they changed; the dialogue, speaker and hidden flag are not touched (`hatchInto` is the full reset). What is ready (an egg, buddies that can evolve) lives in the `ready` atom and is drawn by `view.tsx` in its own box beside the bubble (`NOTICE` in band.ts; `layoutFor` keeps the crew whole and leaves the box out when it does not fit), never in the bubble.
- Evolution: `born[key].stage` counts evolutions spent, `born[key].ats` the turns together when the last one was spent (the next costs `perEvolve` × rarity step, see `evolvesIn`), and `born[key].title` holds the epithet in both languages. `evolveNow` applies `evolve` (bones.ts) and Haiku's new soul (`dreamOn`) only when both succeed; the soul goes into the buddies file.
- Crew: up to `crewSize` buddies out at once (option, default 3). The store's `crew` holds their keys; without it, the comma-separated `active` option, else everyone hatched in roster order; 0.4's single `active` name in the store leads either (`crewKeys`). A newborn joins while there is room (`place`, in commands.ts). `hatchCrew` resolves them into the `members` atom; `members[0]` is the lead. `hooks/band.ts` picks how many of them the band fits into `bodyColumns` × `maxRows` and in what shape; `windowOf` picks which, always the speaker's page. The `speaker` atom is the index of the one whose bubble shows: every quip and canned line passes it on, a click takes it, and `banterChance` lets the next one answer a Haiku quip once, 3s later (`clock.after`).
- The list pane (`/buddy list`, id `LIST_PANE`): `list.tsx` draws it from two atoms in state.ts, `listing` (every buddy as `listingOf` in crew.ts reads it, null while the pane is shut, read again by `refresh` like the band) and `pane` (the pick, filters, mode, the add draft, the last note). Its controls are in `edits.ts`, which reuses the verbs of commands.ts and writes the file fresh (`patchEntry`). Navigation is Tab and Button hotkeys (a hooks module gets no raw keys). Mobile has no `Input`/`Select`, so there it only shows. The sprite is drawn at a fixed tick: an animated pane would redraw its fields 3×/s.
- A rename keeps the store's key: `aka` in the store maps the new name's key to the one the buddy was born under (`keyIn`, in `rosterOf`), so tallies other sessions are still writing land on it. A name whose key someone else holds (`isHeld`) is refused, for a rename and for a newcomer; `forget` drops the buddy's aliases. `crew` holds store keys and is matched on `e.key` before names.
- `hooks/roster.ts` holds per-species lines and hats, generated from coding-buddy (MIT, see `THIRD_PARTY_LICENSE-coding-buddy`).
- The validator only lets `$` be passed to functions declared at the top of a module (it follows them across imports); keep helpers that take `$` at top level. It also reads an atom only in the file that declares it, so every `read`/`update` stays in `state.ts`; other modules call its helpers.
- Check before pushing: `claude plugin validate plugins/buddy` and `claude plugin test plugins/buddy`. For a type-check, use a scratch `tsconfig.json` with `allowImportingTsExtensions` (the modules import each other as `./x.ts`).
